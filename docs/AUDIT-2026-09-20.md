# Molt engine audit — 2026-09-20

This audit follows the production path used by Molt Studio:

**Studio input → source capture → evidence packing → model generation → React build → multi-viewport evaluation → measured repair → interactive review → GitHub export → generated GitHub Action → Netlify production deploy.**

The purpose is to find system-level conflicts and failure ceilings, not merely visual CSS defects.

## High-risk findings addressed in this hardening branch

### 1. Multi-page repair starvation
Previously, a selection of four correction rounds meant four repair calls for the entire website. A seven-page site could spend all four calls on one route and leave other failing pages untouched.

**Hardening:** high-fidelity Studio settings (4/6) now expand only enough to provide at least one direct repair opportunity per page, capped at 20, and route selection prioritizes failing routes with fewer prior repair attempts. Economy settings remain literal. The loop still stops early when all views pass.

### 2. Later-page generation could silently damage earlier pages
All routes share one React workspace. During first-pass generation, a later route could rewrite existing shared CSS/components or an earlier route before the evaluator had measured the completed site.

**Hardening:** after the first route, first-pass generation may add its own route file and new route-specific support files but cannot rewrite an existing shared or earlier-route file. Shared files can still be refined during measured repair, when every route/device is evaluated together.

### 3. Fixed execution ceilings were unsafe for 5–7 page/high-reasoning jobs
The Studio runner previously used a 25-minute agent budget and a 3-minute provider request timeout regardless of page count or reasoning effort.

**Hardening:** Studio jobs now calculate bounded execution budgets from page count, requested repair level, and reasoning effort. Agent time, provider request timeout, output-token ceiling, and request-attempt ceiling scale within fixed maximums. The GitHub job envelope is 80 minutes so the agent can fail/clean up before the runner itself is killed.

### 4. Generated deployments were not reproducible
Generated repositories contained exact direct dependency versions but no lockfile, and their deploy workflow ran `npm install`. Future deploys could therefore resolve a different transitive dependency tree.

**Hardening:** Molt copies the exact trusted render-toolchain lockfile into every generated project before model usage and verifies the generated package dependency sets match it. Generated deploy workflows now use `npm ci`.

### 5. Delivery CI skipped the exact production handoff
The zero-cost delivery test proved GitHub repo creation and direct Netlify API deploy separately, but did not exercise the generated repository's own deploy-on-push workflow.

**Hardening:** delivery CI now creates a temporary private generated repo, publishes a deterministic build fixture, installs the same generated GitHub Action/Netlify helper used in production, waits for that workflow to build and deploy, verifies the public marker, and deletes the temporary repo/site.

### 6. Failed runs left reserved GitHub/Netlify debris
Molt reserves a private repository and Netlify site before paid model usage. If the reconstruction later failed before source handoff, those reservations could remain.

**Hardening:** fatal runs now best-effort delete unused reserved Netlify sites and GitHub repositories when source was never successfully published. If useful React source was published, it is intentionally retained even if later deployment fails.

### 7. Uploaded saved-page bundles accumulated after terminal jobs
Saved ZIP/folder contents remained in Studio storage after the run.

**Hardening:** terminal report/error reconciliation and job deletion now purge the job's uploaded source bundle.

### 8. A legacy paid Ceballos workflow bypassed the current Studio path
The repository still contained a manual live-model Ceballos workflow with its own defaults.

**Hardening:** the legacy paid workflow was retired. The supported paid path is the Studio-dispatched `reconstruct-site.yml` workflow with zero-cost delivery preflight.

### 9. Studio dependency resolution was not reproducible
The Studio used exact top-level dependency versions but did not commit its generated lockfile, so CI/hosting could resolve a different transitive dependency graph later.

**Hardening:** the exact lockfile generated from the unchanged Studio package manifest is now committed, normal Studio CI uses `npm ci`, and the generated-site delivery path has its own independently pinned lockfile as described above.

## Quality blind spots already addressed immediately before this audit

- authenticated interactive preview and comparison media
- overall score plus worst-band score
- hybrid live URL + saved ZIP evidence without allowing the ZIP to downgrade live geometry
- safe carousel Previous/Next interaction capture
- progressive repair acceptance while protecting already-correct views/interactions
- font family, font size, font weight, font style, line height, letter spacing, text alignment and text transform
- inline bold/italic emphasis even when generated markup differs
- horizontal text-block placement
- explicit element-to-element spacing and vertical rhythm
- stricter 97% overall / 92% worst-band acceptance floor
- generated source/preview/GitHub/Netlify handoff

## Remaining known limitations / follow-ups

These are not hidden success claims. They remain explicit engineering limits.

### External deployment cleanup: Railway
The GitHub repository still has two external Railway services posting commit statuses even though the current Studio is hosted on Netlify and Railway is not required. One Railway status is currently succeeding and another is failing, which can make GitHub's aggregate commit status red and may cause unnecessary external builds.

This must be disconnected in Railway/GitHub integration settings; removing a repository file alone does not prove an external Railway project is detached.

### Interaction coverage is intentionally bounded
Molt captures safe reversible states such as details/disclosures, aria-expanded controls, inactive tabs, and recognized Previous/Next carousel controls. It does not claim exhaustive coverage of:
- hover-only menus/effects
- arbitrary drag/swipe behavior
- custom drag/swipe carousels that expose no safe button/tab controls
- authenticated/private states
- destructive or submission actions

### Automatic URL discovery is navigation-based, not a full crawler
Without explicit page paths or a saved bundle, discovery follows homepage header/navigation links and applies the selected page cap. Exact page lists or saved-page ZIPs are preferred for a deterministic 5–7 page client site.

### Saved-file evidence currently defines file-mode route scope
Hybrid file mode combines the live URL with saved evidence, but the saved bundle's page manifest currently defines which routes are reconstructed in that mode. A homepage-only ZIP does not automatically provide saved HTML evidence for six additional live routes. A future product improvement should make optional ZIP evidence independent from live page selection; today, a deterministic multi-page hybrid run should include the relevant saved HTML pages in the bundle or use URL mode with explicit routes.

### Source variability is not yet fingerprinted
Rotating hero content, A/B tests, geolocation, cookie state or time-based content can legitimately produce different screenshots across captures. Molt does not yet run a source-stability fingerprint/retry before reconstruction.

### Very large pages fail closed
The current capture height ceiling is bounded at 26,000 CSS pixels by default and geometry is bounded to 1,400 visible elements per viewport. Molt reports/fails rather than silently pretending oversized evidence was complete.

### Hard cancellation can interrupt cleanup
Normal engine timeout/failure paths have cleanup headroom. A force-cancelled GitHub Actions process can still be terminated before process-level cleanup finishes. Studio reconciliation marks the job cancelled/error; external reservations may require later garbage collection if the operating system kills the runner immediately.

### Owner beta is not a hardened multi-tenant worker
Public URL/DNS checks, Chromium sandboxing, path contracts and secret-stripped build environments are defense in depth. A commercial multi-tenant executor still requires dedicated worker isolation, egress controls, quotas, durable leases/retries and tenant-separated storage.

### Backend services are deliberately not faked
Forms, payments, authentication, ecommerce data, bookings, CRM/email delivery and other business services remain explicit reconnection/migration work. A visually matched frontend does not claim those services were migrated.

## Production acceptance philosophy

A run is not considered visually complete merely because it built successfully. Molt evaluates the complete route/device matrix and retains the best measured source. The target is at least 97% global pixel fidelity and 92% in the weakest measured band, plus content, typography, spacing and captured interaction checks. A result that misses those criteria remains **Needs refinement** instead of being presented as exact.

Passing deterministic CI proves the orchestration and regression contracts. It does not prove that every arbitrary website will reach the fidelity target with a particular model. Live-model quality remains a measured property of each reconstruction.
